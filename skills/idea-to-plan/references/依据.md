# 设计依据（2026-10-20 调研）

> 这份文件回答：**为什么新方案要写这些节、为什么要改对话方式？**
> 只列**我实际读过原文**的来源；每条写"它说了什么"和"我们拿它做什么"。**不把推测写成结论。**
> ⚠️ 这些是**设计依据**，不是"用了就保证 AI 一次写对"的证明。真正的保证还靠契约冻结＋门禁＋审核；我们的流水线还需要一次真实项目试点来验证。

## 1. 规格驱动开发（Spec-Driven Development）

### 1.1 GitHub Spec Kit

- **来源**：<https://github.com/github/spec-kit>（读于 2026-10-20）
- **它说什么**：Spec Kit 把流程做成 `Specify → Plan → Tasks → Implement → Converge`；规格是中心，计划/任务/代码都从规格来。
- **规格模板里有什么**：用户场景与验收场景（Given/When/Then）、功能需求（FR-001…）、关键实体、成功标准、假设；**不确定的地方必须写 `[NEEDS CLARIFICATION]`，不许猜**。
- **我们拿它做什么**：方案必须有"用户场景 + 功能需求 + 关键实体 + 可测的成功标准 + 假设"；不知道的写「待定/未查证」，不许编。
- ⚠️ **边界**：Spec Kit 的 `plan/tasks` 对应大脑的蓝图/任务卡；本 skill **只借它的 spec 部分**，不写 plan/tasks。
- 相关原文：<https://github.com/github/spec-kit/blob/main/templates/spec-template.md>

### 1.2 AWS Kiro

- **来源**：<https://kiro.dev/docs/specs/>、<https://kiro.dev/docs/specs/feature-specs/>（读于 2026-10-20；页面更新 2026-08-04/10-15）
- **它说什么**：每个 spec 生成 `requirements.md`（用户故事 + EARS 验收标准）、`design.md`（架构/时序/错误处理/测试策略）、`tasks.md`（离散可执行任务）；支持按依赖分波并行。
- **EARS 的写法**：`WHEN [condition/event] THE SYSTEM SHALL [expected behavior]`。
- **我们拿它做什么**：每条 AC 用"给定/当/应该"；每个功能先写行为，再写技术；任务按依赖分波（对应我们的 W1..Wn）。
- ⚠️ **边界**：Kiro 的 `design.md` / `tasks.md` 对应大脑的蓝图/任务卡；本 skill **不写这两份**，只借它的 requirements/EARS 写法。

### 1.3 GitHub Copilot coding agent 官方最佳实践

- **来源**：<https://docs.github.com/en/copilot/how-tos/agents/copilot-coding-agent/best-practices-for-using-copilot-to-work-on-tasks>（读于 2026-10-20）
- **它说什么**：好任务要有：**清晰的问题/工作描述、完整的验收标准、要改哪些文件的指引**；**模糊任务不适合直接交给 agent**（"Ambiguous tasks: tasks lacking clear definition"）。
- **另一份实践文档**（社区整理，非官方）：Issue 模板建议包含 Context / Change / Acceptance Criteria / Files to Modify / Do Not Change / How to Test；AC 要绑定具体检查（测试命令、linter、冒烟流程）。
- **我们拿它做什么**：方案必须有"做什么/不做什么/怎么验收/哪些不能动"；文件清单留到大脑看仓库后补（策划阶段不能猜）。

### 1.4 PRP（Product Requirement Prompt）

- **来源**：<https://github.com/Wirasm/prp>（读于 2026-10-20）
- **它说什么**：PRP = PRD + 精选代码库上下文 + agent/runbook；是"让 AI 一次交付可用的最小包"；强调**可执行的验证命令**和**有界范围**。
- **我们拿它做什么**：方案不是纯 PRD；要有"给大脑的上下文 + 验收判据 + 边界"。但策划阶段没有代码库，所以"代码库上下文/文件清单"这一段留给大脑，不硬编。

### 1.5 AGENTS.md

- **来源**：<https://agents.md/>（读于 2026-10-20）
- **它说什么**：AGENTS.md 是给 coding agent 的项目级说明文件（"README for agents"），放构建/测试命令、代码规范、安全注意事项；已被 60k+ 开源项目使用。
- **我们拿它做什么**：确认"给 agent 的上下文要单独写、要具体"是行业共识；但本 skill 不生成 AGENTS.md（那是大脑/项目初始化的事），也不在方案里写技术栈（那是蓝图的事）。

## 2. 需求质量对代码生成的影响（实证）

- **来源**：Larbi et al., *When Prompts Go Wrong: Evaluating Code Model Robustness to Ambiguous, Contradictory, and Incomplete Task Descriptions*, ICSE 2026 / ACM DOI `10.1145/3744916.3773186`；预印本 HTML：<https://ar5iv.labs.arxiv.org/html/2507.20439>（读于 2026-10-20）
- **它做了什么**：在 HumanEval / MBPP 上系统注入三类需求缺陷（歧义、矛盾、不完整），测 7 个代码模型。
- **关键结果**（原文）：
  - 不清晰的任务描述导致 **Pass@1 下降 20–40 个百分点**；
  - **能编译的代码里 60–90% 语义不正确**；
  - 模型**不能可靠区分"清晰"和"不清晰"的描述**（MCC −0.1 到 0.55）——也就是说，**它不会稳定地停下来问你，往往会硬写**。
- **我们拿它做什么**：
  1. 方案必须消歧、补全、去矛盾；不能靠"AI 会自己问"。
  2. 每条 AC 要有具体例子和失败样例——这是在补"不完整"和"歧义"。
  3. 我们自己的流水线也要假设"模型不会稳定提问"，所以方案要把该说的说透。

> **信心边界**：这篇论文测的是**单函数级**代码生成（HumanEval/MBPP），不是多模块真实项目；不能直接外推"方案写好就一定成功"。但它足以支持一个保守结论：**需求缺陷会显著拉低代码正确率，且模型不一定会问你。**

## 3. 对"对话方式"的设计判断（**这是判断，不是论文结论**）

以下几条来自用户反馈＋产品设计常识，**没有**用论文证明；我标成"判断"：

1. **先开放、后选项**：用户想说话时，弹选项会打断表达；选项只适合"他说不出来"的时候。
2. **"以上都不是，我说我的"是坏选项**：它把"否定"和"自由输入"混在一个标签里，用户会误选；自由输入应该是**独立的一句话**，不是第四个选项。
3. **不问预算**：预算不是需求；0 基础用户答不上来，还会以为不选就没法继续。费用只在"查到的事实"里出现。
4. **一次只问一个**：连问会让人只答最后一个；这是对话设计常识，不是实验结论。

> 如果以后要证明"新对话方式更好"，需要做 A/B：同一批 0 基础用户，旧版 vs 新版，看完成率、追问次数、方案返工率。**现在没有这个数据，所以不宣称"已验证"。**

## 4. 我们对"够不够详细"的结论

> **分工前提（用户 2026-10-20 明确）**：契约、蓝图、任务卡都是**大脑**出；方案不替它写。方案的目标是让大脑和用户的几轮对话**问得少、问得准**，不是"一次切完、再也不问"。

**旧方案的缺口**（对照"大脑要聊清楚什么"）：

| 大脑聊的时候要问的 | 旧方案有没有 | 后果 |
|---|---|---|
| 目标/范围/不做什么 | 有，但"不做什么"弱 | 大脑要再确认一遍 |
| 谁用/场景/角色 | 有，但偏标签 | 大脑要追问具体场景 |
| 每个功能的行为/空/错 | 只有"画面"，没有逐功能 | 大脑要回头问 |
| 产品数据概念/状态/权限 | 没有 | 大脑要问"数据长什么样" |
| 每个功能的 AC | 只有一张总表 | 大脑出卡时对不上功能 |
| 产品形态与约束 | 只有"轮子" | 大脑要问手机/网页/几个人 |
| 决策/待定/默认 | 只有"待定"一节 | 大脑遇到未知会停或猜 |
| "大脑可能会问的"清单 | 没有 | 大脑从零问一遍 |
| 人工前置 | 有 | 这块旧方案是好的，保留 |

**新方案的补法**：把**产品事实**写到"大脑不用从零问"的程度；同时把"还没定的"列成**待问清单**，每条给默认——大脑能按默认走的不打扰用户，必须用户拍板的只问那一两个。**不越界去写契约/蓝图/文件清单/测试命令**（那些是大脑的活）。这就是 §1–§13 的来源。

## 5. 还没验证的事（**别当成已证明**）

1. **新方案在一次真实无人值守项目里的效果**：还没跑过对照；需要一次试点（同一需求，旧方案 vs 新方案，比较大脑聊的轮数、追问次数、卡返工率、门禁红率）。
2. **14 条自检闸的误杀/漏杀**：还没积累足够样本；先按"严进宽出"用，遇到误杀再调。
3. **结构化体检脚本**：只查结构，不查语义；不能替代人判。
4. **外部政策/费用**：一律现场查，30 天过期；本文件不写任何费率/天数。

> 结论：**有把握的是"旧方案不够、新方案补上了哪些具体缺口"；没把握的是"新方案能把追问/返工降到多少"。** 后者要用试点数据说话，不能拍脑袋。
